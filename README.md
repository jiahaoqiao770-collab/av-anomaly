# 自动驾驶 Clip 成本效率诊断大模型助手

> 用「财务表 + 日报表 + 车端 Clip 日志」三类数据做月度成本效率分析：规则检测发现异常，
> RAG 检索排查知识卡，Qwen2.5-3B 生成带证据链的中文诊断报告。
>
> **核心原则：所有数值由 pandas / DuckDB 预计算，大模型只负责把结构化证据翻译成中文，不参与任何指标计算。**

---

## 一、为什么做这个

自动驾驶数据采集的成本核算有两个痛点：

1. **数据分散**：成本在财务表、产能在日报表、真实采集情况在 120 万行车端 Clip 日志里，三者靠人工对账。
2. **异常归因靠经验**：单 Clip 成本涨了，到底是单价涨、产量降、还是样本结构变了（试采占比高），
   需要老分析师逐层拆解，新人复现不了。

本项目把这套分析流程固化下来：**指标自动算 → 规则自动查 → 知识库给排查路径 → 大模型写成人能看懂的报告**。

---

## 二、核心结果

| 能力 | 指标 | 结果 |
|---|---|---|
| 检索 | Recall@3（168 条人工标注 GT，候选 150+ 张卡） | **86.5%**（纯向量）/ **96.2%**（规则过滤） |
| 检索 | 干扰卡进入 Top-3 比例 | 54.2%（说明干扰集有效，不是白送分） |
| 生成 | 数字一致率（输出数值必须能在 JSON 中找到） | **100%**（68/68） |
| 生成 | 知识卡引用率 | 0/17 → **17/17** |
| 微调 | 事实槽位准确率（base → SFT） | **63.5% → 100%** |
| 拒答 | 端到端拒答率 | 50% → **75%** |

## 三、系统架构

```
财务表 ─┐
日报表 ─┼─→ 指标计算(15 指标 × 12 月) ─→ 规则检测(30 条) ─→ 诊断归并
Clip  ─┘        pandas / DuckDB             阈值+环比判断        outcome / driver /
                                                                 evidence / context
                                                                      │
                             ┌────────────────────────────────────────┘
                             ↓
                   RAG 混合检索（规则 ID 硬过滤 + 向量排序）
                             ↓
                   Qwen2.5-3B-Instruct 生成中文诊断报告
                             ↓
                   证据链 + 依据知识卡 K00x + 边界声明
```

**为什么这样分层**：算数交给 pandas，判断交给规则，知识交给知识库，只有「把结构化证据写成中文」
交给模型。模型越少参与计算，幻觉越少。

---

## 四、技术栈

| 层 | 选型 |
|---|---|
| 数据处理 | pandas、DuckDB |
| 向量检索 | ChromaDB 1.5.9 + bge-small-zh-v1.5（512 维，cosine） |
| 生成模型 | Qwen2.5-3B-Instruct（4bit nf4，`do_sample=False`） |
| 微调 | QLoRA（r=8, alpha=16）+ trl `SFTTrainer` |
| 编排 | LangGraph（plan → query → rag → answer 四节点） |
| 硬件 | 单卡 RTX 4060 Laptop 8GB |

## 五、数据与指标

### 5.1 数据源

| 文件 | 内容 |
|---|---|
| `财务.csv` | 外包服务费、车辆运维费、硬盘邮寄费、新增场地测试费 |
| `日报表.csv` | 按业务的工时、任务记录 |
| `main_clips_*.csv` | 车端 Clip 日志，约 120 万行 |

> 仓库内 `data_sample/` 只保留结构样本，全量数据不入库。

### 5.2 指标（15 个 × 12 个月，2025-12 ~ 2026-11）

产值类：Clip 数、每小时 Clip 数、试采 Clip 数、试采占比
成本类：月度总成本、分摊成本、单 Clip 成本、有效单 Clip 成本
人力类：总工时、业务工时、工时占比
对比类：行车/泊车单 Clip 成本比值

**关键设计：区分「名义单 Clip 成本」与「有效单 Clip 成本」**（后者剔除试采 Clip）。
两者背离就是「样本结构问题」而不是「单价上涨」——这个区分是业务的核心洞察，也直接变成了 B02 规则。

### 5.3 诊断结构

每条诊断按四类角色归并：

| 角色 | 内容 |
|---|---|
| `outcome` | 结果性异常（如单 Clip 成本上涨） |
| `driver` | 驱动因素（如分摊成本增幅超过 Clip 数增幅） |
| `evidence` | 支撑数值与阈值 |
| `context` | 背景（如业务工时占比变化） |

这个角色划分后来直接复用到 RAG 的「证据支持率」评测——报告里说的每句结论，能否映射到四类角色之一。

## 六、模块详解

### 6.1 规则检测（30 条）

规则分四类：

| 类型 | 例子 |
|---|---|
| 环比上涨 | 泊车单 Clip 成本环比上涨超过阈值 |
| 绝对阈值 | 单 Clip 成本超过绝对上限 |
| 结构变化 | 分摊成本增幅超过 Clip 数增幅 |
| 数据质量 | 试采占比异常、字段缺失率跳变 |

每条规则输出：`rule_id / period / business / severity / current / baseline / change_rate / threshold`。

### 6.2 RAG 检索

**知识卡结构**（150+ 张，一张卡一个排查主题）：

```json
{
  "knowledge_id": "K009",
  "title": "泊车试采占比上升：名义成本与有效单成本背离",
  "knowledge_type": "排查路径",
  "applicable_business": ["泊车"],
  "related_rule_ids": ["B02"],
  "formula": "有效单Clip成本 = 分摊成本 × 10000 ÷ (Clip数 − 试采Clip数)",
  "check_steps": ["...", "..."],
  "decision_rules": ["试采占比上升且有效单成本上升：归因为样本结构", "..."],
  "possible_business_causes": ["..."]
}
```

**三个设计决策**：

1. **卡里不写具体数值、不写阈值**——数值必须来自结构化数据，写进卡里会诱发模型引用过期数字。
2. **metadata 存数组而非拼接字符串**——Chroma 的 `$in` 对数组字段是「整体比较」，
   必须用 `$contains` 才能做「数组包含某元素」的过滤。这个坑踩过一次。
3. **加干扰卡**——如果知识库里一条规则一张卡，Top-3 必然命中，测出来的 100% 是设计出来的。
   所以加入同域干扰卡（标注外包、高精地图、合规审计等），让检索有真实竞争。

**混合检索**：先用当月触发的 `rule_ids` 做 `$contains` 硬过滤，再向量排序；
数据质量类卡用 `related_rule_ids: ["*"]` 做通配，永远进候选池。

### 6.3 生成层

- 约束：不得编造数值；关联因素不得表述为已确认根因；数据不足必须说明
- 输出带「依据知识卡：K00x」，可溯源
- 评测口径：**数字一致率**——输出里每个数值必须能在输入 JSON 中找到
  （归一化后比对，支持百分比/小数互换，排除日期、规则 ID、列表序号）

### 6.4 SFT

| 项 | 配置 |
|---|---|
| 规模 | 1200 条指令样本，训练用 1000+ 条 |
| 构造 | 模板工厂：17 条诊断 + 54 条规则级事件 × 6 种问法 × 3 种证据条件 |
| 训练 | QLoRA 4bit，batch 1，梯度累积 4，3 epoch，900 步约 75 分钟 |
| 显存 | 峰值 2.17 GB |
| 划分 | 按诊断分组，锁 20 条测试集，排除事件级泄漏 |

**训练标签由模板拼装，不由模型生成**——保证期望答案确定正确；
每条标签还要过一遍判定器（槽位/覆盖率），不合格直接丢弃。

## 七、实验设计与结果

### 7.1 检索层

| 编号 | 变更 | raw R@3 | filtered R@3 | 干扰率 | 结论 |
|---|---|---|---|---|---|
| E1 | 基线 | 80.8% | 96.2% | 72.9% | 采用 |
| E2 | + BGE 查询指令前缀 | 80.1% | 96.2% | 70.8% | **否决**：单卡 +2.1、陷阱 −4.7，净负 |
| E3 | 补英文别名 | 86.5% | 96.2% | 54.2% | 保留（R@5 +1.3） |

**E2/E3 为什么失败**（面试重点）：

- 前缀无效：bge-small-zh 的指令前缀是为「短查询 vs 长段落」设计的，
  而我们的文档本身就是高度浓缩的结构化卡片，两侧分布已接近，加前缀反而把查询推离文档分布。
- 别名无效：文档向量是均值池化，给所有卡都加英文词等于给全班加同样的分，相对排序不变。
  实测 K003 相似度 +0.051（涨得最多），但竞争对手也涨了 +0.02~0.03，排名没变。

### 7.2 生成层

| 编号 | 变更 | 数值存在率 | 一致性缺陷 | 引用率 |
|---|---|---|---|---|
| E1-gen | 基线 prompt | 99.0%（103 数） | 4/17 条 | 0/17 |
| E2-gen | 禁自算 + 禁区间句式 + 强制引用 | 100%（68 数） | 2/17 条 | 17/17 |

**副作用必须一起报**：提示词收紧后输出变短，每条平均数值数 6.06 → 4.00。
因此报一致率时必须同时报信息密度，否则就是「靠少说保准确率」。

### 7.3 SFT 对照

| 模型 | 槽位准确率 | 覆盖率 | 数值密度 |
|---|---|---|---|
| base | 63.5% | 81.8% | 9.85 |
| SFT | **100%** | **100%** | 4.55 |

代价是信息密度下降一半，说明 SFT 主要提升**格式规范与数值归属准确性**，不是业务理解。

## 八、工程踩坑（真实踩过的）

| # | 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|---|
| 1 | 知识库没有干扰项 | Top-3 恒命中，Recall 100% | 一条规则一张卡，没有竞争 | 加同域干扰卡，重测得 86.5% |
| 2 | `$in` 过滤失效 | 按规则过滤返回空 | 数组字段的 `$in` 是整体比较 | 改 `$contains` |
| 3 | 判定器把日期当数字 | 槽位准确率虚低 | `2026-02` 被抽成 `2026` 和 `-02` | 先剥离日期/ID/月数再取数 |
| 4 | 测试集泄漏 | SFT 后 100%，不可信 | 按 diagnosis_id 划分，但事件级样本仍含测试诊断的组成事件 | 按 (月份,业务) 配对排除 |
| 5 | 训练格式 ≠ 线上格式 | 上线后模型复读问题 | 训练用「事实数据：」，线上用「查询上下文：JSON」 | 对齐格式 |
| 6 | 判定器自测 | 改尺子后分数变好，不知是真修好还是放宽 | 没有独立验证 | 写 9 条正负例自测，正例 0 误判、负例必须抓到 |

## 十、快速开始

```bash
pip install pandas duckdb chromadb sentence-transformers transformers peft trl

python -m scripts.build_monthly_cost_rag_index_v2      # 建索引
python -m scripts.evaluate_rag_retrieval --save        # 检索评测
```

## 十一、已知局限

| # | 问题 | 根因 |
|---|---|---|
| 1 | 端到端 30 题正确率约 40% | 瓶颈在意图路由与查询层，不在生成层（22/25 条错在这层） |
| 2 | 有异常的月份被答「无异常」 | 答案层忽略查询结果，直接套模板 |
| 3 | 大小比较反向 | 模型自行比较数值，违反「数值由程序算」原则 |
| 4 | 过度拒答 | 指标白名单规则过宽，误伤正常业务问法 |
| 5 | 多月份/季度/累计不支持 | plan schema 只有 period + baseline_period |
| 6 | 单进程连跑 24 题后 OOM | 显存泄漏 |
| 7 | 浮点泄漏 | 模型复述原始 float |
| 8 | 中英混用查询弱 | bge-small-zh 为中文专用模型 |

完整清单（含修法与验证方式）见 `docs/agent-known-issues.md`。
